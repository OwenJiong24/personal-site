**结论**：把一个内部工具开源，不是一次 `git push`，而是一次以「证明没有任何私密内容被带出去」为交付物的审查。Vox 的代码早就准备好了；发布这一步花在密钥扫描、零历史仓库、纯文本脱敏，以及一个会改变项目自我描述的许可证发现上。

2026-11-18 我发布了 [vox-windows](https://github.com/OwenJiong24/vox-windows)——一个 Windows 语音输入工具：按住热键、说话、松手，文字出现在光标处。这篇讲的是发布过程，不是产品说明书。

## 1. 一个让人不舒服的起点

早期的一份项目文档记载：一个真实的云 API key 曾以明文进过 git 历史，之后被清洗。我没有只信文档。我用 pickaxe 搜了全部提交里的 key 前缀，找到了那条提交信息直接写着「历史已重写」的记录。无论有没有 key 幸存，一个结论无法回避：**带着原仓库的历史发布，不是一个选项**。

所以发布仓库完全没有历史：一次全新的 `git init`，一个初始提交，34 个文件。没有任何祖先提交可能夹带旧密钥。这是一个有意的取舍——公开仓里丢掉了开发故事，换来一句能诚实说出口的话：从未发布过任何历史 blob。

## 2. 密钥扫描真正抓到了什么

对当前工作树跑密钥模式扫描，交付代码里没有明文 key——但更宽的审查找到了另一类东西，它们不是「凭据」意义上的秘密，却正是泄露型发布的主要成分：

- 写进默认 prompt 的开发者名字；
- 硬编码在某个字符串里的具体显卡型号，每个用户都会看到；
- 纠错词表和测试夹具里的一整个业务词表（一个跨境电商税务词、三个支付/公司名称）；
- 注释和测试里某人桌上的麦克风型号；
- 两个启动脚本里某台机器的绝对路径。

这些都不会让构建失败。但它们都在告诉读者一些作者没有选择公开的事。我逐一换成通用写法：显卡字符串变成 `NVIDIA GPU (CUDA)`，prompt 变成通用的软件工程句子，纠错词表围绕通用开发词重写。

**经验法则**：密钥扫描抓的是 key。发布审查还必须单独抓身份、硬件和词表——这三样东西会把一个匿名的开源项目变成一次自我暴露。

## 3. 谁都想不到的许可证约束

源码是 MIT。我查了已安装依赖的元数据而不是靠猜，有两个包会改变任何要打包再分发的人的实际处境：

| 依赖 | 许可证 | 为什么重要 |
|---|---|---|
| `zhconv`（繁转简） | **GPLv2+** | 以库方式调用；打包后的二进制可能继承 GPL 义务 |
| `pystray`（系统托盘） | **LGPLv3** | 动态导入；打包构建必须保留声明并允许重链接 |

其余都是宽松许可证（MIT / BSD / Apache-2.0 / PSF）。我写了一份 `THIRD_PARTY_NOTICES.md`，直说：Vox 源码是 MIT，但聚合后的整体带着上面两条义务。如果不写这句就把整个项目称为「MIT」，那会是一个小小的、看似合理的、错误的说法——正是这个站存在的意义要抓的东西。

## 4. 我实际跑过的证据清单

1. 全历史 pickaxe 搜 key 前缀 → 找到历史重写提交 → 用零历史发布。
2. 工作树密钥扫描 → 交付文件无明文 key；真实配置（含加密 key）排除在发布树外。
3. 身份/硬件/词表专项 → 名字、显卡型号、业务词、麦克风名、机器路径全部替换。
4. 发布树与已验证源码做 diff → 只有文本改动，零逻辑改动；因此在源码上跑过、115 项通过的离线门禁，对发布版依然成立。
5. `git init` → 一次提交 → 推送 → 用托管方 API 核对远端 34 文件树里没有 `config.json`、没有日志、没有运行时状态。

**实测**：离线回归 115 通过 / 0 失败；发布版语法检查全绿；远端树 34 个文件；敏感文件存在数 = 0。

## 5. 一个能直接抄的结构

如果你正要把内部工具开源，直接拿这张决策表：

| 问题 | 是 | 否 |
|---|---|---|
| 曾经提交过任何凭据吗？ | 新仓库，零历史 | 保留历史 |
| 代码里写了名字 / 硬件 / 客户词表吗？ | 纯文本脱敏，再 diff 证明逻辑没动 | 跳过 |
| 有 GPL/LGPL 依赖吗？ | 附带声明，重新斟酌「MIT」措辞 | 直接说 MIT |
| 能核对*远端*文件树而不只是本地吗？ | 推送后用托管 API 列文件 | 别声称干净 |

重点不是 Vox 有多重要。重点是「开源」有一个可验证的定义：当你能拿出远端文件树、diff 和许可证声明的那一刻，你才真的做完了——在那之前，你只是推了代码。
