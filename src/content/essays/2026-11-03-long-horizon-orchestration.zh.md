**结论**：两套编排不在同一条赛道上。DSH 的 Super-agent 原型是单宿主内的完整系统，规则可以写进代码；我们的是跨模型、跨 harness 的拼装，规则只能写在文档里，由人执行。本文只做事实对照：两套系统各自的结构、解决的问题、付出的代价，以及 DSH 在哪些点上明显更强。文末是 OJ 的两条判断和三条可被证伪的预测。

## 一、事实：两套系统的参数

| 项目 | DSH Super-agent 原型 | 我们的系统 |
|---|---|---|
| 运行基底 | 一个宿主进程，一套插件 API，一个 SQLite | 多个 harness 的独立会话，文件总线，少量脚本 |
| 事件入口 | 插件级 Source（GitHub、飞书），带读位点与 bot 身份 | 收件箱文件、CLI、人转发、一个任务管道 |
| 身份 | agent 自己的 bot 账号 | 借用人类账号，按供应商分裂 |
| 规则强制 | 宿主代码强制：gate、Mandate、工具白名单 | 文档规则、收口检查、人的最终判断 |
| 状态载体 | 单库（trigger/ticket/outbox 等表） | 一本账、收件箱、台账表、看板、对齐包 |
| 调度单位 | 事件；Router 批处理，Worker 占槽 | 工作批：按趟车与块排期 |
| 成本约束 | token 与缓存 | 配额：订阅额度、免费车道、额度耗尽交班 |
| 失败形态 | 进程死、卡住、重放 | 会话断、上下文丢、席位等人、转发脱节 |
| 变更频率 | 宿主版本慢变量 | 席位每周重排，车道随时退役 |
| 人的角色 | operator，处理例外 | 路由器、审批人、排期者、生产操作员 |

## 二、各自解决的问题

| 问题 | DSH 的解法 | 我们的解法 |
|---|---|---|
| 任务归属 | Ticket 有 ID、Mandate、Assignment | 一本账记计划号，回执带号 |
| 事件连续 | Thread 订阅，事件直送执行者 | 收件箱路由，人转发 |
| 授权 | 代码 gate，强度分 explicit/inferred，模式 off/observe/auto | 类授权 A–E，越界清单，逐件裁定 |
| 失败恢复 | 单库幂等，重启不重放，30 分钟后台超时 | 回执、检查点、人工捞回 |
| 成本控制 | 模型调用预算 | 配额套利：免费车道轮换、按成功率退役 |
| 生产风险 | 不在系统设计范围内 | 人在场，生产写入保留在人工边界 |
| 组织变化 | 假设组织稳定 | 编制每周重排，按最后一张表为准 |

## 三、设计取舍

| 选择 | DSH | 我们 | 买到什么 | 付出什么 |
|---|---|---|---|---|
| 规则落地 | 宿主代码 | 文档＋人 | 写文档快，改规则快 | 漏检无法被系统发现 |
| 状态 | 单库 | 多视图账本 | 跨机、跨供应商可读 | 对账成本，编号多套 |
| 调度 | 事件 | 批次 | 批次减少人的审查次数 | 长尾事件响应慢 |
| 路由 | 常驻轻量模型 | 人（CEO/CTO） | 判断质量高，能处理模糊情况 | 人的注意力是瓶颈 |
| 执行 | 隔离目录＋槽位 | 席位＋车道 | 可换模型、可换 harness | 连接问题多，上下文重载 |
| 变更 | 架构稳定 | 编制流动 | 能按额度与人数随时收缩 | 规则要反复解释，文档臃肿 |

## 四、DSH 明显更强的点

以下按事实列出，不涉及我们。

1. 强制。gate、Mandate、工具白名单在宿主代码里，prompt 改了也绕不过。我们的规则在文档里，执行靠人和模型自觉，系统无法证明规则被遵守。
2. 一致性。单库、生成列、outbox 去重、重启不重放。我们有六套编号（决定、任务、裁定、流水、计划、回执），多时钟，多视图；自动化第一步是对账，不是路由。
3. 可复现。公开 benchmark、参数、对比图，实验可以重跑。我们的数字是过程观察，没有对照组。
4. 文档体系。按序阅读、每篇只依赖前文、Rejected concepts 表、policy version。我们的共识是时间序流水，新席位接入成本高。
5. 身份。agent 有自己的 bot 账号，权限边界清楚。我们借人类账号，边界靠约定。

结论：在「让系统自己跑」这个目标上，DSH 的实现比我们的完整。这是事实判断。

## 五、我们不照抄的原因

| 条件 | DSH 的前提 | 我们的现状 |
|---|---|---|
| 接口稳定 | 一套宿主 API | 每月有模型、配额、prompt 格式变化 |
| 事件量 | 团队级，持续不断 | 一人公司的开发事件，量级小 |
| 集成成本 | 一次写进宿主 | 每个 harness 要重做一遍 |
| 人的位置 | operator 只处理例外 | CEO 同屏，生产风险必须有人把关 |
| 变更频率 | 架构是慢变量 | 席位与执行每周变 |

判据：一个流程该不该写成代码，看四条同时成立吗——接口跨三个以上 harness 稳定、动作确定、失败可被程序检出、事件量乘集成成本小于人工成本。四条不满足时不写代码，改用文档和人。

这是成本选择。不是我们的方法更好，是当前接口不稳定、事件量小，代码化的维护成本高于人工。代价是状态一致性差、审计靠人、人的负担重。

## 六、OJ 的两条判断

> 「AI 永远会出错会偏离——因为信息不对称，用户不可能给出 100% 脑子里的信息。长期不检查，AI 编排就会偏离。所以从核心目标出发做车道方向的持续对齐，是我这里最困难的事，也是各类 agent 编排没有解决的。我们需要海量微型决策给 AI 做纠偏，这种生长性很难很累，但是会有长期价值——比如所有的原始输出和校准的上下文可以在模型能力上升之后复用和消化。所以长程编排的本质还是要和用户一起进化而非单向增加——这是信息对齐的成本造成的。」
> —— OJ 2026-11-03 会话原话

> 「我对海量浪费 token 和额度有一定的抗拒，我认为本地模型作为那个路由和处理的机制才是合理的，否则海量 token 其实就算成本低也是高于基础需求的，这是价值定位的差异。」
> —— OJ 2026-11-03 会话原话

在两条判断之上，结构是这样：

| 层 | 做什么 | 频率 | 判据 |
|---|---|---|---|
| 人 | 不可逆决策、审美、风险 | 低 | 做错了收不回来 |
| 本地模型 | 路由、分类、记账、对账、格式 | 高 | 可逆、规则可描述 |
| 前沿模型 | 推理、难题、终审 | 低 | 需要通用能力且错不起 |

自检问题：一件事做错了，损失能不能被账本下一轮发现？能，交给本地模型和账本；不能，留给人。

校准语料：原始输出、纠偏理由、当时的上下文。存下来。能不能跨模型代复用，是第七节的验证项，不是结论。

## 七、可反驳的预测

1. 以「减少人工介入」为目标的编排，在真实业务上运行一个季度内，会出现一次方向性偏离，系统自身不会发现。定义：连续三次产出被推翻或返工，原因在方向不在执行。核对：2027-02-03，翻账本数次数。
2. 同一批历史消息重放，本地路由的单位决策成本低于前沿路由；下一代模型接入后，本地路由与本人实际决定的一致率差距缩小。核对：2027-05-03，公布重放结果。
3. 下一代模型接入后，固定 50 个校准点重放，所需人工微决策数下降。核对：下次主力模型升级后两周内，公布数字。

三条都能被证伪，数据都来自我们自己的账本。

## 八、我们的失败清单

1. 席位等人：任务在等一条转发，人不知道要转发。账本里没有「谁在等谁」这个状态。
2. 文档注水：规则靠自觉执行，文档越来越厚，遵守越来越薄。
3. 六套编号：决定、任务、裁定、流水各一套号。自动化第一步变成对账。
4. 车道退役：两条车道因最近 20 次尝试成功率 36% / 38% 被自动退役。这条是系统做对的。
5. 告警积压：一天 22 条告警没有投递，告警通道自己断了。

## 九、结论

两套系统平行。

DSH 那套在其约束下更完整：单宿主、代码强制、单库、可复现。我们的在其约束下是适应：接口不稳定、配额受限、人必须在场，所以把规则留在文档，把判断留给人。

代价写在第五节：状态一致性、审计可靠性、人的负担。改进方向是减少人的记账量，不是把判断写成代码。第七节列了可验证项，到期公布结果。
